# pi-ecode 界面设计

本 Skill 用于在真实的 pi-ecode 代码库中做 UI 工作，不生成独立设计稿。始终先遵守仓库 `AGENTS.md` 与用户要求；本文件只补充设计方法，不放宽需求澄清、方案确认、改动范围、测试或 Git 门禁。若任务只要求审查或解释，提供有证据的建议，不擅自修改代码。

## 1. 先确定任务与现状

- 用一句话写明用户打开受影响界面要完成什么；区分新功能、Bug 修复、视觉调整和只读审查。需求会改变行为但边界未定时，按项目流程先澄清；需要实施时按项目流程先提出方案并取得确认。
- 阅读实际挂载路径、状态来源、焦点与滚动行为、相邻组件及样式。先搜索现有 token、组件、图标和动效模式，不根据截图或 CSS 类名猜测实现。明确哪些状态需要覆盖：空、加载、进行中、完成、失败、禁用与快速反向（按任务取舍）。
- 区分观测到的问题和个人审美判断；不要为局部改动重构其他界面。

## 2. 设定一个贴合任务的方向

- 以本项目已有的安静、本地优先工作台为起点。明确本次界面的信息主次、主要操作、内容密度和唯一视觉重点；有现成设计或用户指定风格时沿用，不重新发明配色。
- 桌面界面优先真实工作密度、稳定列宽和共用对齐线。以 1100×720 为主，兼顾 820×560；对长对话、长工具输出和窄窗口检查滚动、溢出与可点击区域。
- 先用间距、对齐、字重和表面层次表达分组；添加边框、卡片、阴影或装饰前，问它承担了什么无法由这些手段完成的任务。复杂工具面板、代码与差异审查允许有功能性分隔，避免机械地“去掉所有线”。
- 使用现有 `src/renderer/styles/tokens.css` 语义 token 与邻近 UI 约定。不要照搬 Vetta 的 Tailwind 类、默认靛蓝模板、字体包或画布目录，也不要为了观感平添依赖。

## 3. 实现有目的的交互

- 在编码前按仓库的 UI 设计流程列出相关交互的动效决策表：交互、目的、动效类型、时长/曲线、进入/退出及中断、降级方式。没有交互价值的元素可明确保持静止。
- 动效服务空间关系、状态反馈或进度；状态反馈优先短 transition。流式文本和工具输出增量不得因重渲染反复入场。处理快速开关、退出后卸载、隐藏期间 `inert`/焦点、`prefers-reduced-motion`；先让逻辑状态生效，不让动画阻塞操作。
- 优先复用现有交互组件。按钮、选择、表单和错误提示必须同时检查键盘操作、可访问名称、焦点可见性和失败反馈；不只靠颜色或动画表达状态。

## 4. 用真实结果自审

- 用与用户任务一致的内容检查：中文较长文案、真实路径和工具日志、空与错误状态；不要用占位数据证明布局正确。重点看边缘对齐、意外换行、裁切、图标可见性、文字对比度和视觉主次。
- 若当前任务和环境允许截图或交互检查，应以实际渲染结果修正问题；先看图再改，避免连续盲调。没有视觉验证条件时如实说明，不将类型检查或 CSS 字符串断言当作动画实际播放的证据。本仓库不自动启动预览/开发服务器，由用户自行部署目测。
- 实施后按 `AGENTS.md` 执行类型检查、测试、构建、差异审查与提交；只汇报已验证结果和仍需人工目测的事项。只读审查任务不提交。

## 适用边界

这是 pi-ecode 项目级 Skill，仅在当前项目被 pi 信任且被选为工作目录时自动发现。它不提供 Vetta 的 `.vetd` 画布、`vetd_*` 工具、元素定位或自动截图能力。模型根据上方描述决定何时加载；若需强制调用，可在消息中使用 `/skill:pi-ecode-ui-design`。
